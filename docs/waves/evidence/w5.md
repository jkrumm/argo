**It is not telemetry, HyperDX or OTel, and it is not in the committed source.** It is local `node_modules` state.

`VITE_HYPERDX_API_KEY` set vs unset changes the total by 37 B. The main checkout's own build of the same commit is
2,315,864 B: its `node_modules/.bun` still holds `shiki@4.4.3` / `@shikijs/*` from an older install (not in `bun.lock`;
argo declares none), so `basalt-ui/content`'s lazy highlighter resolves and Vite emits ~28 grammar/theme chunks
(`tsx` 16 KB, `jsx`, `javascript`, `typescript`, `css`, `html`, `python`, `sql`, `go`, `shellscript`, `engine-javascript`, …,
~190 KB gzip, all lazy). In the clean build those chunks are 126-byte stubs:
`throw Error('Could not resolve "@shikijs/langs/tsx" imported by "basalt-ui". Is it installed?')`.

Consequences:

- Wave 3's 2.13 MB came from a clean tree; Wave 4's 2.32 MB and the 1.41 baseline's 2,329,235 B from this machine's
  stale tree. The baseline→w3 "drop" (2.33 → 2.13 MB) is mostly the same artifact, not the stubbed charts.
- **Open (Wave 6, content): argo's lockfile has no shiki, so production code blocks cannot highlight** (production
  1.41 did not either). Either add `shiki` + `@shikijs/langs` + `@shikijs/themes` as deliberate deps (+~190 KB lazy) or accept
  unhighlighted code. A build that prints chunks which throw on load is itself basalt friction (see Left behind).
- `make evidence` measures whatever is installed. Compare bundle numbers only across `--frozen-lockfile` trees.
