# Hermes Chat v2 — Spec and Implementation Guide

> **Supersedes `docs/HERMES-CHAT-PRD.md` and `docs/HERMES-CHAT-PHASE-B.md`.** Both are stale in
> ways that would actively mislead a rebuild — they name a retired `packages/charts`, a rejected
> sandboxed-iframe diagram design, the Blueprint palette, `check-theme.mjs`, an audio-proxy that no
> longer exists, and AI SDK v5. Read this file instead; the old two are kept only as history.

> Status: **specified, not started.** Grounded in a 2026-08-02 audit of `argo`, `basalt-ui` and the
> installed `hermes-agent v0.19.1`.

---

## Verdict

The Hermes chat surface in Argo is not missing — it is built, merged and running in production. It
is also, in order of severity: streaming-unstable in a way that is now fully explained, blind to
tool calls, and roughly a quarter reimplementation of modules `basalt-ui` already ships and Argo
imports zero of.

Three numbers frame the work:

| Measure                                                                | Value                  |
| ---------------------------------------------------------------------- | ---------------------- |
| Lines in `apps/dashboard/src/features/hermes-chat/`                    | ~4,500 across 27 files |
| Of those, pure reimplementation of shipped `basalt-ui` modules         | ~1,200                 |
| `basalt-ui/agent` + `basalt-ui/content` imports in the dashboard today | 0                      |

The rebuild is therefore not "add features". It is: fix the streaming contract at the server, grow
`basalt-ui` into the framework that makes the client correct by construction, then rebuild the
client on it in one pass.

### Why the proxy is not optional

The Hermes listener is not a browser-addressable endpoint, and this is not a matter of taste:

| Constraint                                                                               | Evidence                                                                        |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| CORS is off — a browser cannot reach it at all                                           | no `API_SERVER_CORS_ORIGINS` configured                                         |
| The bearer is host-privileged: the same key opens `/api/jobs` with full cron CRUD        | `api_server.py:1940-1947`; live probe returned 43 KB including every job prompt |
| Binds the tailnet IP only, no TLS                                                        | `lsof` → `<tailnet-ip>:8642 (LISTEN)`                                           |
| Hermes has no stream resume or replay anywhere                                           | `api_server.py:6677-6680`                                                       |
| Run state is in-process; a gateway restart vaporizes it (18 starts logged, 5 in one day) | `api_server.py:1343-1358`                                                       |

What _is_ right about the instinct to remove it: the proxy currently does far too much. It re-encodes
Hermes SSE through `streamText` with the SDK's default `maxRetries: 2` against a **tool-executing**
agent. The thin-proxy principle in D4 is the correction.

**Defects 2 and 3 are live in production and are the reported duplication.**
`~/vps/apps/argo/compose.yml:99` sets `REDIS_URL: redis://redis:6379` and the redis container has
been up for weeks, so resumable streaming is on. Defect 2 makes a single resume render the previous
reply followed by the new one; defect 3 makes the resume fire more than once. Together they account
for the symptom without needing any other explanation.

The prod query bears this out with a caveat worth keeping attached: `SELECT thread_id, role, status,
count(*) FROM argo.hermes_message GROUP BY 1,2,3 HAVING count(*) > 1` returns 0 rows in production
(2026-08-02). The unfiltered grouping returns 10 groups, all count = 1 — max group size is 1, not
merely under 2, and every row is `status='complete'`, so defect 5's interrupted-turn row has never
actually been written. Caveat: the table holds only 10 rows across 5 threads (2 per thread), nothing
newer than 2026-06-18 — a near-dormant write path, so the empty result is consistent with
render-only duplication but is not proof the write path is safe.

One correction to a plausible-sounding theory, since it will otherwise be re-derived: `hermes.ts:759`
does call `resumeExistingStream` without `skipCharacters`, so replay _is_ from character 0 — but that
is **correct and required**. v7's `reconnectToStream` is a bare GET that sends no `Last-Event-ID` and
no offset of any kind (zero hits across all of `ai@7.0.18`), so the server has nothing to skip from.
Do not "fix" it.

One feed, three kinds of row, Slack-shaped rather than chat-shaped.

The ladder above started at 1.9.0 and shifted by one on 2026-08-02: 1.9.0 was released from
`basalt-ui` `master` carrying only the chart-layer batch while B1 sat unpushed on its branch, so B1
lands as 1.10.0 and every phase after it moves up. Versions are computed by semantic-release from
the commit types, not chosen — if this table and a published tag ever disagree again, the tag wins.

Two design decisions from that spec are load-bearing and should not be quietly reversed during
implementation. First, **the `AgentPart` union stays closed**: foreign parts are a separate
`ForeignPart` type resolved through consumer renderer → re-narrow → exhaustive switch → fallback.
Folding them into the union would make `assertNever` accept everything, which is the opposite of the
point. Second, **the sanitize hook is a data extension, not a function** — a
`(base: Schema) => Schema` callback can return `{}`, an additions-only object cannot express removal,
and basalt appends its sanitize pass _after_ consumer `rehypePlugins` so the escape hatch cannot
outrun it.

One guard cannot be a lint rule alone: defect 1 is cross-package, and a single lint run over the
dashboard sees only `ai@7` and passes. Hence the split — an in-file rule plus a workspace-walking
`doctor` check.

## Implementation playbook

The orchestrator holds the plan and the verdicts. It does not grind through reads, multi-file edits
and validation loops — that is what the workers are for.

### Per-phase loop

1. **Research gate.** Any library fact — a v7 signature, a `resumable-stream` option, a Mantine
   prop — goes through `/research` first. Nothing in this program is answered from memory; the
   ecosystem moved two AI SDK majors since the last write-up.
2. **Brief.** Write the complete brief before delegating: exact paths, the change, acceptance
   criteria, intent, scope limits, and **the resolved library facts from step 1**. A subagent cannot
   see research the orchestrator already did.
3. **Delegate.** `@implementer` for settled multi-file work. Parallel implementers only on
   **disjoint** file groups — a running implementer exclusively owns the files it touches, and
   running `/check` over those paths mid-flight produces spurious failures.
4. **Validate.** `mcp__sideclaw__check` — never a format/lint/tsc/test loop inline. It is
   asynchronous: the call returns a `jobId`, then `job_wait` until it stops returning
   `stillRunning`.
5. **Review.** `/review` on the diff. Use `--deep` for A1 and A2 — the streaming contract and the
   idempotency invariants are exactly where a plausible-but-wrong change survives a shallow read.
6. **Verify in the browser.** `/browse` against the running dashboard, walking the reproduction
   table. This is the gate that catches what tests cannot: double replays, lost messages, mid-fence
   flicker.
7. **Commit.** Conventional commits, one logical concern. Argo is direct-to-master. Fold follow-up
   fixes into the commit that introduced them with `/commit --amend` — never ship a single-line fix
   commit.

### Repo-specific rules

| Repo           | Flow                                                                                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `basalt-ui`    | **PR-required and NPM-published.** Always its own commit, never mixed with a consumer change. Minor versions only — never a major. `bun run build` before testing any consumer against it     |
| `argo`         | Direct-to-master. Push triggers RollHook → rolling restart on the VPS                                                                                                                         |
| `hermes-agent` | Touch only for A6's doc correction. Prompt/SOUL.md shaping is a **separate manual task in that repo** — never inside an Argo loop. `/hermes-validate` and `/hermes-update` are its own skills |

### Round-trip discipline

Each `basalt-ui` release is a real round-trip: commit in `basalt-ui` → PR → merge → release → `bun
update basalt-ui` in Argo → `bunx basalt-ui sync` → `check-theme` + `oxlint` → commit in Argo. Batch
B-phases whose API shapes settle together; three round-trips beat four, and four beat six.

### What stays with the orchestrator

Deciding, verifying, and holding the thread of intent. Specifically: reading review verdicts rather
than diffs, judging browser evidence, and choosing when a phase is actually done. Editorial work
tightly coupled to source already in context — this document, the migration record — stays inline
too; handing it off means re-passing all the source in the brief.
