# API ClickHouse reads: Line and Machines

Moved from `apps/api/AGENTS.md`. Read before changing `/line/*`, `/machines/*` or the ClickHouse read path.

## Line (ClickHouse read path)

`/line/{now,uptime,latency,router,speedtests}` serve the home internet line's history from ClickStack's ClickHouse, where linewatch exports it (service `linewatch-app`, metrics `line.*`, log events `line.outage.*`; contract: linewatch `docs/DESIGN.md` §Export and retention). Tag `Line`; one endpoint per dashboard card, so a failing query is one error card; ClickHouse unconfigured, unreachable or erroring answers `503 {"error":"line data unavailable"}`.

- `clients/clickhouse.ts` owns the connection: plain `fetch` (through `tracedFetch`, span `clickhouse <query name>`) against the HTTP interface, no `@clickhouse/client` (the whole read path is one POST). The user is `argo_ro` (SELECT on `default.*`, `readonly=1`, 15 s and 1 GB per query; vps `docs/observability.md` §Dashboard read access), so a query sends **no settings** (no `SET`, no `max_execution_time` URL parameter: ClickHouse refuses them in readonly mode; the format is the `FORMAT JSON` clause). Values travel as typed `{name:Type}` placeholders filled by ClickHouse from `param_<name>` URL parameters; the credential travels in the `Authorization` header, never the URL or a span.
- Env: `CLICKHOUSE_URL` (the plist: `http://vps:8123`, the VPS's tailnet name; empty = off), `CLICKHOUSE_USER` (default `argo_ro`), `CLICKHOUSE_PASSWORD` (`.env.tpl`: `op://vps/clickstack/ARGO_RO_PASSWORD`, resolved by `launch.sh` like every ref, fail-closed). The reachability grant is the tailnet ACL `tag:devhost` -> `tag:vps` `tcp:8123`.
- `lib/line-queries.ts` holds every query as a constant plus its row mapping. A request picks a `window` (`24h`, `7d`, `30d`, `90d`, bucket 5 min / 1 h / 6 h / 1 UTC day) and nothing else: no SQL, table or metric name from the browser. Every query filters on the time column (`TimeUnix`, `TimestampTime`: the sort keys, so partitions prune), pins `deployment.environment.name = 'prod'`, and ends in a `LIMIT`; the tests assert that for each one.
- Semantics worth knowing: loss is `100 x (1 - sum(received) / sum(sent))` over the 30 s probe cycles, RTT the median of the per-cycle medians; outages come from the `line.outage.duration` gauge (kept 400 days, the log events 30), internet scope only, an open outage from an `opened` log with no `closed`; `state` is `stale`, never `up`, when the newest probe sample is older than 3 minutes (an export cannot cross a dead line, so a live outage shows as `stale` until it closes). Router history starts when linewatch's router export started; errored seconds and interface throughput are not read.
- Tests (DB-free, in `make check`): `clients/clickhouse.test.ts` (fake HTTP interface), `lib/line-queries.test.ts` (query contract, mapping, clipping, state), `routes/line.test.ts` (bearer, window validation, 503s).

## Machines (host metrics from ClickHouse)

`/machines/{overview,detail}` serve host and container metrics of every machine from the same ClickHouse read path as Line (`clients/clickhouse.ts`; tag `Machines`; 503 when it is unavailable, 404 on `detail` for a host that did not report in 24 h). The agents are OpenTelemetry collectors with `service.name=host-agent` (host metrics `system.*`, grouped by `host.name`); containers come from `docker_stats` and, until the agents carry them, from the older `host-probe` service (`CONTAINER_SERVICES` in `lib/machines-queries.ts`, duplicates averaged).

- `lib/machines-queries.ts` holds every query as a constant plus the maths; a request picks a `range` (`1h`, `24h`, `7d`, `30d`; buckets 1 min, 5 min, 30 min, 2 h, so at most 400 points per series) and `detail` a host name (`^[A-Za-z0-9._-]{1,64}$`) that reaches ClickHouse only as a `{host:String}` placeholder; an empty host means every machine.
- Semantics: CPU is `100 x (1 - idle)` over all cores, memory the `used` state (Linux and macOS differ in the other states), load the 1-minute average beside `cores`, the fullest filesystem by mount; the "now" values are the newest sample, not a bucket. A machine whose newest sample is 10 minutes old (`SILENT_AFTER_S`) is `silent`: current values null, never zero. Network and disk IO are cumulative counters: the rate of a bucket is the rise since the series' previous bucket over the elapsed time, summed over devices, a counter reset or a hole of more than one empty bucket is a gap (`counterRates`). Network skips tunnels, loopback, bridges and virtual interfaces (`VIRTUAL_DEVICE`). `reportingPct` is the share of buckets with a sample since the machine's first in the range; `gaps` are the silent stretches of 10 minutes or more.
- Tests (DB-free, in `make check`): `lib/machines-queries.test.ts` (query contract, rate maths, silence, mapping), `routes/machines.test.ts` (bearer, validation, placeholder-only host, 404/503).
